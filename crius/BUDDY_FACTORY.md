# OTHRYS BUDDY FACTORY

> Status: CANONICAL PRODUCT-FAMILY SEED — architecture and commercial discovery doctrine, not implementation proof.
> Owner: CRIUS / House of Crius
> Existing anchor product: Study Buddy
> Mission: turn the proven Study Buddy pattern into a reusable consumer-app factory rather than a collection of unrelated one-off apps.

## 0. Thesis

OTHRYS should distinguish its internal mythological machinery from the names normal customers see.

Inside OTHRYS: Titans, organs, gates, evidence, routing, memory, builders and control systems.

Outside OTHRYS: products whose names explain themselves.

Canonical consumer pattern:

`[DOMAIN] BUDDY`

Examples:

- Study Buddy
- Travel Buddy
- Collector Buddy
- Career Buddy
- Home Buddy

The word `Buddy` is a product-class signal: a bounded, user-serving companion for a specific life or work domain. It should not imply unrestricted autonomous authority.

## 1. Brand architecture

Working hierarchy:

`OTHRYS -> Buddy Platform -> Domain Pack -> Buddy Product`

Examples:

`OTHRYS -> Buddy Platform -> Education Pack -> Study Buddy`

`OTHRYS -> Buddy Platform -> Travel Pack -> Travel Buddy`

`OTHRYS -> Buddy Platform -> Collection Pack -> Collector Buddy`

The consumer app may lead with its descriptive Buddy name while retaining an OTHRYS endorsement where useful: `Study Buddy — by OTHRYS`.

Naming law: clarity beats mythology at the consumer surface. The family should be coherent enough that a user who understands one Buddy immediately understands the role of another.

Names remain working names until trademark, app-store, domain, language and collision checks are completed. Never assume a descriptive Buddy name is legally ownable merely because it is clear.

## 2. Buddy Core

The economic thesis is reuse. Study Buddy should eventually be mined for a reusable core rather than cloned blindly.

Candidate common substrate:

- identity and account;
- profile/preferences;
- domain-scoped memory;
- file/document/media ingestion;
- structured extraction;
- search/RAG;
- conversational interface;
- timeline/history;
- dashboard;
- tasks/checklists;
- notifications/reminders;
- recommendation engine;
- evidence/source links;
- import/export;
- privacy/permissions;
- analytics/value-event telemetry;
- feedback loop;
- cost controls;
- model/provider routing;
- offline/local capability where appropriate;
- subscription/entitlement hooks kept disabled behind CRIUS gates during Course Mode;
- affiliate/referral hooks kept disabled until separately qualified;
- domain-pack interface;
- admin/support surface;
- backup/recovery;
- deletion/retention controls.

A Buddy is not `chatbot + prompt`. The domain pack must change the workflows, data model, tools, evidence, UI and value events.

## 3. Buddy Factory

Factory flow:

`DOMAIN PAIN -> RESEARCH -> REUSABLE-CORE FIT -> DOMAIN PACK -> THIN PROTOTYPE -> VALUE TEST -> OPERATIONAL PROOF -> PUBLIC TEST -> CRIUS REVIEW`

Factory objective:

> Each successful Buddy should make the next credible Buddy cheaper, faster and safer to produce.

Target metric: measure percentage of each new Buddy supplied by tested shared infrastructure versus new domain-specific code.

Never force a domain into Buddy Core merely to maximize reuse. Shared code that damages domain fit is false economy.

## 4. Buddy admission test

Before a new Buddy earns a build candidate state, answer:

1. Is there a recurring domain problem rather than a novelty prompt?
2. Does persistent context/memory materially improve the result?
3. Are there multiple related workflows that benefit from one domain model?
4. Can the product produce a concrete value event?
5. Can output quality be evaluated?
6. Does Buddy Core plausibly supply a large part of the product?
7. Is there a plausible distribution path?
8. Is there a plausible commercial path even if the app remains free?
9. What sensitive data does the domain create?
10. What could go badly wrong if the Buddy acts or advises incorrectly?
11. Is the market already saturated by products that solve the whole job substantially better?
12. What unique OTHRYS organ/data/workflow gives us an edge?

Records, routines, supplies, appointments, documents and care history. Avoid replacing veterinary expertise.

#### Car Buddy

## 6. Do not create Buddy soup

Not every feature deserves an app.

Rules:

- Merge overlapping jobs into a stronger Buddy when separation adds no value.
- A narrow Buddy may begin as a fishing line and later become a module of a larger Buddy.
- Domain specificity must justify a standalone product.
- `X Buddy` is not permission to mass-generate low-quality wrappers.
- CRIUS should kill weak Buddy candidates aggressively.

Possible consolidation examples:

- Exam Buddy and Course Buddy may remain Study Buddy modes.
- Job Hunt Buddy and Interview Buddy may remain Career Buddy modules.
- Warranty Buddy may remain Home Buddy/Tech Buddy functionality.
- LEGO/Watch/Coin/Stamp/Postcard/Toy Buddy may become specialist packs inside Collector Buddy unless independent demand proves otherwise.

## 8. Shared learning flywheel

The factory should learn across products without leaking domain-private user information.

Shared lessons can include:

- ingestion reliability;
- retrieval quality techniques;
- notification timing patterns;
- UI patterns;
- model/task routing performance;
- cost optimization;
- generic failure modes;
- evaluation methods;
- onboarding patterns;
- export reliability;
- infrastructure incidents.

Domain/private content remains governed by product permissions and privacy policy.

Flywheel:

`ONE BUDDY FAILURE -> GENERIC LESSON -> BUDDY CORE IMPROVEMENT -> REQUALIFY AFFECTED BUDDIES`

## 11. First factory missions

### BF-01 — Study Buddy archaeology

Inventory the existing Study Buddy implementation and classify every meaningful component:

`GENERIC BUDDY CORE | EDUCATION DOMAIN | PRODUCT-SPECIFIC | LEGACY/DEBT | UNKNOWN`

Do not refactor during archaeology.

### BF-02 — Buddy Core extraction plan

From BF-01, define the smallest reusable substrate. Prefer extracting proven patterns over designing a grand framework from scratch.

### BF-03 — Travel Buddy pack

Use actual travel workflows to identify the first second-domain test of Buddy Core. The purpose is not merely to ship Travel Buddy; it is to prove whether the factory abstraction survives a radically different domain.

### BF-04 — Collector Buddy pack

Use collection workflows as a second contrast case: structured objects/provenance/images/value evidence rather than lessons or itineraries.

### BF-05 — CRIUS market scan

For the top 10 Buddy candidates, investigate competitors, distribution, price structures, user pain, affiliate/partner possibilities, white-label buyers, data/privacy burden and smallest value test.

### BF-06 — Naming clearance

Before public branding, perform trademark/domain/app-store/search/language/collision checks. `Buddy` is the architecture pattern; individual public names may need modifiers or alternative marks if collisions are unacceptable.

## 12. Factory success criteria

The Buddy Factory becomes real only when:

1. Study Buddy remains operational after any extraction work.
2. A documented Buddy Core exists in code, not only prose.
3. A second Buddy is produced materially faster because of the core.
4. A third Buddy proves reuse was not a one-off coincidence.
5. Shared components have tests/evidence.
6. Domain packs remain genuinely domain-specific.
7. privacy/security boundaries survive reuse.
8. CRIUS can score and gate each product independently.
9. one Buddy can fail commercially without contaminating the others.
10. common infrastructure improvements can be propagated and requalified safely.

## 13. Canonical principle

> **OTHRYS builds the machinery. Buddies make the machinery useful to normal people.**

And:

> **Do not build twenty apps twenty times. Build one trustworthy factory, then earn every domain pack.**
