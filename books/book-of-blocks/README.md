# The Book of Blocks

**Status:** CANONICAL OTHRYS OS HOUSE MAP — subordinate to the harvested Book of Blocks doctrine.

## Definition
A **Capability Block** is a versioned, provenance-bearing, user-meaningful reusable product capability with an explicit contract, bounded authority/data/effects, independent acceptance proof and an owned lifecycle.

A Block is **not** a helper function, UI atom, Titan, Star, provider, workflow, whole Oros or control-plane service.

## Forge stock vs official composition stock
Levels 1–2 intentionally generated many small tested units. Keep them, but classify them honestly:
- **Primitive** — deterministic helper/operation such as slugify, checksum, canonical JSON or retry policy.
- **Pattern** — proven composition/engineering pattern made from primitives.
- **Capability Candidate** — evidence-backed user-meaningful product outcome not yet admitted.
- **Capability Block** — canonical specimen with maturity and proof.

Small Primitives are the **Forge stockroom** used to build Capability Blocks. They do not inflate the official Block count.

## Maturity
`RAW -> PROVEN -> REUSABLE -> CERTIFIED -> GOLDEN` with `RETIRED` as terminal eligibility state. Normal Factory reuse begins at `REUSABLE`, not merely because a folder is named Block.

## Composition
Blocks expose provider-neutral `provides / requires / optional` contracts. Bridges satisfy provider/integration edges. Product-specific adapters/glue remain explicit. Consumers use canonical source; fork-per-Oros is forbidden.

## Ownership
OTHRYS OS/Hub doctrine governs Block law. Canonical reusable Capability Block implementation belongs in the dedicated `othrys-blocks` repository. OTHRYS OS may retain training primitives and admission/evidence records without becoming a second Block source.

## Relationship to Oros and Stars
Blueprint declares capability need. Factory resolves exact eligible Blocks/Bridges. The Oros runs them. Stars observe/manage resulting operational domains. **Block != Star.**
