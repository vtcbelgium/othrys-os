Date: 2026-09-08

## Why this exists

A valuable earlier OTHRYS commercial thesis was fragmented across the legacy CRIUS House and was at risk of being obscured by newer market scans. Hyperion inherits it.

The central idea is not merely to sell OTHRYS, nor merely to sell templates or consulting. OTHRYS can become a **product factory and evolutionary portfolio engine**:

`DISCOVER PAIN -> PRODUCE SMALL PRODUCT -> DEPLOY -> OBSERVE REAL USE -> KILL / KEEP / EXPAND -> QUALIFY -> OPEN FINANCIAL GATE WHEN PERMITTED -> COMPOUND WINNER -> RETAIN / LICENSE / SPIN OUT / SELL`

This is now a Hyperion strategy primitive.

## 1. Automatic Website / Tiny-Product Factory

The recovered Distribution doctrine described a `Tiny-tool fishing fleet`:

`PAIN QUERY -> TINY USEFUL TOOL -> ORGANIC DISCOVERY -> MEASURE -> KEEP / KILL / EXPAND`

The stronger interpretation is an **automatic website/product maker**. OTHRYS should eventually be able to manufacture, deploy, instrument and maintain many narrow public web products at low marginal cost.

Candidate output classes:
- calculators
- checkers
- converters
- generators
- diagnostics / Doctors
- comparison pages
- compatibility tools
- public benchmarks
- niche directories
- monitoring pages
- data explorers
- micro-SaaS
- upload -> process -> download tools
- pay-per-run agents
- small domain-specific Buddies
- installable plugins/extensions
- downloadable verified workflow packs

The factory does not assume every output deserves monetization. Most experiments may die. Cheap failure is a feature.

## 2. Evolution, not prediction

Do not require Hyperion to correctly predict the winner before launch.

Use many bounded experiments and let evidence select winners.

Minimum telemetry:
- impressions/search discovery
- visits
- activation/start
- successful completion
- repeat use
- sharing
- retention
- explicit paid intent
- conversion once legally permitted
- refunds
- support burden
- compute/API cost
- gross margin
- failure rate
- organic growth

Product states:
`SEED -> GENERATED -> VERIFIED -> PUBLIC EXPERIMENT -> SIGNAL -> WINNER CANDIDATE -> COMMERCIAL QUALIFICATION -> FINANCIAL GATE -> SCALE -> STRATEGIC ASSET`

Possible terminal states:
`KILL`, `ARCHIVE`, `OPEN SOURCE`, `KEEP FREE`, `BUNDLE`, `LICENSE`, `SPIN OUT`, `SELL`.

Popularity never opens the financial gate automatically. Popularity creates a high-priority qualification packet.

## 3. Winner doctrine

A hit is not simply a traffic spike.

A winner shows some combination of:
- repeat usage
- organic acquisition
- strong task completion
- low support requirement
- low marginal cost
- users asking for more
- users asking for paid capability
- defensible data/history
- high-value workflow dependency
- measurable economic value
- strong marketplace/store traction

When one hits:
1. preserve the working product;
2. understand why it hit;
3. harden operations;
4. map monetization surfaces;
5. qualify legal/admin/economic readiness;
6. open only authorized channels;
7. create adjacent variants around the proven demand;
8. decide whether it belongs inside OTHRYS or deserves independent identity;
9. build transferable operating history and clean rights;
10. periodically evaluate retain vs licence vs spin-out vs sale.

## 4. One product can create a constellation

Recovered second-order-product doctrine remains important.

Example:
`TOOL OLYMPICS -> BENCHMARK DATA -> PUBLIC RESULT PAGES -> SEARCH TRAFFIC -> NEWSLETTER -> AFFILIATE/SPONSOR INVENTORY -> PAID HISTORY/API -> CERTIFICATION -> PRIVATE BENCHMARK -> PROCUREMENT INTELLIGENCE`

Likewise:
`WEBSITE DOCTOR -> FREE SITE SCORE -> SEARCH/SHARING -> PAID DEEP REPORT -> MONITORING -> WORDPRESS PLUGIN -> BENCHMARK DATA -> HOST/TOOL AFFILIATE -> WEBSITE QUALITY INDEX`

Hyperion must therefore score both **first-order revenue** and **second-order optionality**.

## 5. Grey-Zone Lab inheritance

`GREY` means commercially non-obvious or boundary-sensitive, never illegal/deceptive.

Preserved legitimate patterns:
- free diagnostic -> paid cure
- useful free product -> qualified commercial lead
- sponsor pays while user remains free
- open-source wedge -> paid scarce complements
- disclosed affiliate revenue with independent ranking
- shared-savings economics
- verified outcome pricing
- free public benchmark -> paid private benchmark
- public intelligence -> paid depth/history/API/alerts
- useful directory -> disclosed referral economy
- independent certification/requalification
- controlled experimental exhaust -> derived intelligence
- dormant IP resurrection
- product as proof-of-capability
- white-label invisible engine
- reverse freemium: individuals free, organizations pay
- procurement intelligence

Hard rejects remain:
- hidden commercial relationships
- fake reviews/engagement
- spam
- dark patterns
- undisclosed sponsorship
- prohibited scraping or rights violations
- secret payout-driven rankings
- user-data misuse
- platform-term evasion
- fake scarcity
- disguised income

If legality/benefit status/platform terms are uncertain: `LEGAL_REVIEW_REQUIRED`, not assumed permission.

## 6. Build, harvest, acquire, resurrect

The legacy acquisition room adds an important factory input.

The factory may obtain raw material through:
- new generation/building
- harvesting reusable internal OTHRYS code
- packaging dormant internal IP
- adopting/forking compatible open source
- contributing upstream
- legally acquiring rights
- reviving neglected niche products
- using public datasets with permitted reuse
- pattern harvesting followed by independent reimplementation where direct reuse is not allowed

Commercial advantage can come from better selection, packaging, verification and resurrection, not only invention.

## 7. Distribution is part of manufacturing

A product is incomplete if nobody can discover it.

Every factory output should receive a distribution hypothesis before public launch:
- search intent
- marketplace/plugin ecosystem
- GitHub/package registry
- shareable report/badge
- public benchmark/result page
- newsletter/Prometheus
- directory/listing
- partner distribution
- free utility feeding an owned audience

Prefer ecosystems with existing demand over requiring `othrys.be` to manufacture all traffic from zero.

The factory should be able to publish outward while retaining OTHRYS as the hidden production/control plane.

## 8. Low-touch constraint

Current operator preference is explicit: do not recreate a customer-service job.

Factory products score higher when they provide:
- instant checkout
- instant delivery
- self-service configuration
- automated preflight
- automated self-test
- evidence/health report
- automated diagnostics
- docs/AI support
- self-service export/cancellation
- no bespoke tenant code

Penalty:
- discovery calls
- onboarding calls
- recurring meetings
- custom reports
- manual fulfilment
- bespoke integration
- support that grows linearly with customers

Law:
> SELL THE MACHINE OR THE RESULT, NOT YOUR TIME.

## 9. Verification as brand moat

The factory should not become a spam cannon producing fragile AI slop.

Every output should aspire to `OTHRYS VERIFIED`:
- exact dependencies
- compatibility matrix
- test fixture
- expected result
- setup validator
- health check
- known failure modes
- cost envelope
- last verified date/version
- execution receipt where appropriate

Law:
> It works, or it tells the user exactly why it does not.

Verification limits factory throughput by design. Ten verified useful products beat ten thousand untrusted pages.

Do not force a subscription where a one-time purchase or pay-per-run better matches value.

## 11. Strategic asset / exit doctrine

Do not build for hypothetical acquisition, but build winners so they *could* be transferred.

A mature winner should accumulate:
- independent users
- clean usage history
- brand/domain where useful
- clean IP/licensing
- documented operations
- reproducible deployment
- economics
- retention history
- datasets with clear provenance/rights
- low founder dependence

Then Hyperion can compare:
`KEEP CASHFLOW | BUNDLE | LICENSE | WHITE-LABEL | SPIN OUT | PARTNER | SELL`

Sale is an option, not the objective.

## 12. Automatic factory control loop

Long-term target:

`PROMETHEUS` discovers changing demand/problems/tools.
`HYPERION` scores opportunity and economics.
`Mnem/Atlas/Rhea` retrieve prior knowledge and avoid rediscovery.
`FORGE/HEPHAESTUS` manufactures candidate products.
`TOOL OLYMPICS/SWITCHYARD` chooses reliable low-cost builders/models.
`EVIDENCE GATE/THEMIS/TALOS` verifies and controls release.
`OTHRYS WEB / external ecosystems` publish experiments.
`TELEMETRY` observes real-world evidence.
`HYPERION` kills, expands, bundles, qualifies or prepares monetization.
`FINANCIAL GATES` remain independent and fail closed.

This is not yet claimed as implemented automation. It is recovered strategy and an architectural target.

## 13. Factory economics

A candidate should be scored on:

`EXPECTED_VALUE = DEMAND_SIGNAL * VALUE_PER_SUCCESS * REUSE * DISTRIBUTION_FIT * SELF_SERVE_FIT * SECOND_ORDER_OPTIONALITY - BUILD_COST - RUN_COST - SUPPORT_BURDEN - LEGAL_RISK - PLATFORM_DEPENDENCE`

Portfolio-level metric:
- cost per experiment
- median time idea -> verified public test
- kill speed
- winner rate
- cost per winner
- revenue per winner when gates open
- percentage of revenue not requiring human fulfilment
- cross-product reuse
- product resale/licensing optionality

The goal is not maximum product count. It is **maximum learning and asset creation per unit of operator attention**.

## 15. Course Mode

During Course Mode:
- factory design: allowed
- product generation/testing: allowed subject to normal safety/governance
- free/public experiments: only when operational/public gates are satisfied
- commercial research/preparation: allowed
- live revenue: forbidden while global financial lock remains locked

A hit during Course Mode must be preserved and prepared, not prematurely monetized.
