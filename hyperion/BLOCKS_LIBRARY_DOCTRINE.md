# HYPERION BLOCKS LIBRARY — DEMAND, CONVERSION & COMMERCIAL PSYCHOLOGY

> Status: CANONICAL DESIGN DOCTRINE — not implementation proof.

## Mission

OTHRYS can build excellent products indefinitely and still create little economic value if nobody discovers, trusts, understands or acts on them.

Hyperion therefore owns a specialized section of the OTHRYS Blocks Library: **honed demand and conversion Blocks**.

These are not generic ad widgets. They are reusable, evidence-driven patterns for helping the right visitor discover value, understand it, trust it, take the next useful action, and — when the financial gate is open — buy through an appropriate channel.

Law:
> **BUILDING CREATES SUPPLY. HYPERION CREATES THE CONDITIONS FOR DEMAND TO FIND, TRUST AND ACT ON IT.**

## 1. Every product gets commercial potential analysis

Every public OTHRYS product — from a poker strategy/reference site to a basic-agent setup guide, calculator, Doctor, Buddy, directory or developer utility — gets a Hyperion potential packet before/around release:

- visitor intent;
- likely search/discovery paths;
- audience sophistication;
- recurring vs one-shot use;
- natural next action;
- relevant products/services/tools users may genuinely need;
- affiliate possibilities;
- sponsor possibilities;
- ads suitability;
- direct paid-product possibility;
- email/alert usefulness;
- API/data/pack possibilities;
- cross-product routes;
- trust sensitivities;
- monetization density ceiling;
- expected support burden;
- legal/platform/disclosure constraints.

The result selects Blocks. It does not blindly inject them.

## 3. Subtlety law

A product should feel like a good product, not a monetization Christmas tree.

Hyperion chooses the **minimum commercial surface capable of capturing reasonable value**.

Default rules:
- core task first;
- no giant affiliate wall above the answer;
- no popup before first value unless evidence strongly justifies it;
- no irrelevant affiliate products;
- no repeated CTA every viewport;
- no fake editorial recommendation;
- no sponsor control of truth/ranking;
- no monetization mechanism that makes the site visibly worse than the incumbent we intended to beat.

Measure **revenue per unit of trust/friction**, not raw click yield alone.

## 6. Intent-specific composition

Blocks must be selected by product and visitor intent.

Example: **basic agent setup guide**
- answer/tutorial immediately;
- verified compatibility/version block;
- copyable setup block;
- troubleshooting block;
- optional contextual hosting/API/tool recommendation;
- disclosure beside commercial recommendation;
- related agent-readiness/checker tool;
- no generic shopping carousel.

Example: **poker strategy/reference site**
- useful strategy/reference content first;
- calculators/reference tools where lawful and appropriate;
- clear distinction between educational content and any commercial surface;
- jurisdiction/platform review for any gambling-related commercial relationship;
- no manipulation toward gambling spend;
- no monetization path that depends on encouraging harmful play.

The same Block library can serve radically different products without making them look templated.

## 7. Block qualification

A Hyperion Block is not canonical merely because an AI generated it.

Each serious Block should eventually carry:
- purpose;
- eligible contexts;
- prohibited contexts;
- evidence/research basis;
- variants;
- mobile behavior;
- accessibility requirements;
- disclosure requirements;
- telemetry contract;
- success metric;
- failure metric;
- trust cost;
- test history;
- last qualified version.

Lifecycle:
`IDEA -> RESEARCHED -> PROTOTYPE -> TESTED -> QUALIFIED -> BLOCK -> MONITORED -> RETIRED/IMPROVED`

## 8. Conversion without corruption

Hyperion optimizes:
`RIGHT VISITOR -> FIRST VALUE -> TRUST -> NEXT USEFUL ACTION -> REPEAT VALUE -> COMMERCIAL ACTION WHEN APPROPRIATE`

Not:
`VISITOR -> INTERRUPTION -> PRESSURE -> CLICK`

A short-term conversion gain that damages retention, reputation, organic distribution or product utility can be negative expected value.

## 9. Research loop

Prometheus/Hyperion should continuously harvest:
- high-performing public patterns;
- reputable UX/conversion research;
- marketplace patterns;
- ad/affiliate changes;
- pricing experiments;
- competitor funnels;
- complaints and abandonment reasons;
- successful niche-site structures;
- failed growth tactics;
- platform-policy changes.

Promising patterns enter the lab, not production automatically.

`OBSERVE -> HYPOTHESIZE -> BUILD BLOCK -> TEST -> MEASURE -> QUALIFY -> REUSE -> RECHECK`

## 10. Anti-slop coupling

Every Block and every composed commercial surface must pass Hyperion Anti-Slop.

Reject:
- generic AI marketing copy;
- irrelevant CTAs;
- affiliate stuffing;
- ad density that harms utility;
- fake scarcity;
- fake testimonials/social proof;
- deceptive defaults;
- forced continuity/hidden subscription;
- disguised advertising;
- manipulative cancellation friction;
- dark patterns;
- claims without evidence;
- conversion tricks that win a click and lose a user.

## 11. Metrics

Hyperion measures the whole system:
- qualified discovery
- first-value completion
- return rate
- trust/complaint signals
- CTA relevance
- conversion
- revenue per visitor when permitted
- revenue per active user
- revenue per support minute
- revenue per maintenance minute
- affiliate EPC where relevant
- ad revenue vs retention impact
- organic growth
- cross-product activation
- refund/cancellation
- lifetime value where meaningful
- operator attention

A monetization Block that raises revenue 10% but destroys 25% of repeat usage is suspect until lifetime economics prove otherwise.
